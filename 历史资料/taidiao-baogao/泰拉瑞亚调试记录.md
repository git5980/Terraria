## 三、虚拟屏输入注入调查（未解决）

### 现象
`input.tap` 返回成功，但屏上应用**毫无反应**。

### 修复的两个真实 bug（已编译进新 daemon）

1. **displayId 从未生效**
   上游用 `InputEvent.class.getMethod("setDisplayId", int.class)` 解析隐藏 API。
   Android 14+ 上该方法非 public → `NoSuchMethodException` → `setDisplayIdMethod = null`
   → 注入事件 displayId 恒为 0 → 全部路由到**主屏**。
   **修法**：public → `getDeclaredMethod` + `setAccessible` → `MotionEvent` 三级回退。
   实证日志：`InputController setDisplayId resolution: public`

2. **失败被静默吞掉**
   `ok = (Boolean) injectInputEventMethod.invoke(...)` —— `injectInputEvent` 返回 void，
   强转恒假，注入失败无任何输出。**修法**：不再强转，打印真实返回值。

构建补丁位于 `vscreen/build/build.sh` 的 **stage 1b**。

### 仍然失败的结论
即使 displayId 正确（日志：`inject displayId=32 source=0x1002 ret=true`），事件依然**到不了应用**：

| 检查 | 结果 |
|---|---|
| Unity `UnityPlayer.onTouchEvent` hook | 零调用 |
| `Activity.dispatchTouchEvent` hook | 零调用 |
| 系统自带 `/system/bin/input -d 34 tap` | 无反应 |
| 系统 `/system/bin/input -d 34 keyevent HOME` | 无反应 |
| 窗口层级 | display 上 Activity `Resumed`、窗口持有焦点，完全正常 |

**结论**：Android 16 对"注入事件 → 虚拟屏窗口"的路由限制（虚拟屏无关联输入设备）。
连系统自带 `input` 工具都投递不到，不是 daemon 构造事件的问题。

**踩坑**：`InputManager.injectInputEvent(event, mode)` 第三个参数是 **mode（只接受 0/1）**，
不是 policyFlags；传 `0x01000000` 会得到 `IllegalArgumentException: mode is invalid`。

### 4.2 create/调用物品的方法

```js
// 用游戏自己的 SetDefaults 正确初始化物品（2 参数重载）

// 参数： (int type, bool noMatCheck)
```

**枪械判定**：`useAmmo == 97`（子弹）且 `ranged == 1` → 扫出 **24 把**；
再按名称含"枪/炮"补充 **14 把**特殊弹药枪械 → 共 **38 把**。

### 4.3 五个必须记住的坑

1. **`NativeFunction` 参数个数必须与声明严格一致**
   否则 `bad argument count`。`il2cpp_class_get_name` / `field_get_name` / `field_get_offset`
   只接受 **1 个参数**（类/字段指针）；`il2cpp_domain_get` **无参数**；
   按名查字段用 `il2cpp_class_get_field_from_name(cls, name, 0)`（**3 参**）。

2. **值类型参数要按 4 字节对齐写入**
   `PlaceChest(int x, int y, ushort type, bool notNear, int style)` 中，
   `ushort`/`bool` 若只用 `writeU16`/`writeU8`，高位残留垃圾 → 类型非法 → **必然失败**。
   全部改用 `writeS32` 后一次成功。

3. **跨线程调用托管方法必挂**
   从 Frida 线程调用游戏函数（`SortInventory`、`PlaceChest`、`get_myPlayer`）会抛
   `NullReferenceException`，因为内部要访问 `Main.player[Main.myPlayer]` 等托管对象。
   **游戏主线程调用完全正常**。→ 必须用 `Interceptor.attach(Main.Update)` 在主线程执行。

4. **JsHook 卸载脚本不会移除已装的 hook**
   `frida_unload` 只重置脚本状态；旧 hook 回调引用的作用域已失效 →
   回调抛错并**阻塞后续 hook**。→ 换脚本前先 `Interceptor.detachAll()`，
   或把逻辑全部写在同一个脚本里（安装 hook 后不要再执行新脚本）。

5. **`SolidTile` 有多个同名重载**
   `il2cpp_class_get_method_from_name(cls,"SolidTile",2)` 可能取到错误重载
   （实测世界底部 y=1190 也返回 false）。不要依赖它判断图块。

## 五、成功的操作细节

### 5.1 无敌
```
immune@976     = 1
immuneTime@980 = 2000000000   （≈386 天 @60fps，防止倒计时失效）
immuneNoBlink@977 = 1         （不闪烁）
```
实测：状态稳定保持，用户确认生效。

**注意**：`noKnockback`(2025) / `noFallDmg`(2870) **会被游戏每帧重置**，写字段无效，
要做防击退/防摔必须 hook 伤害函数。

### 5.2 锁定白天（hook 方案）
`dayRate` 每帧被游戏重置回 1，**写字段无效**。改用 hook：

```js
// Main.UpdateTime() 的 native 地址 = MethodInfo.readPointer()（methodPointer 在偏移 0）
Interceptor.attach(updateTimeFn, {
  onEnter: function() {
    if (dayAddr.readU8() === 0) dayAddr.writeU8(1);
    var t = timeAddr.readDouble();
    if (t < 26000 || t > 28000) timeAddr.writeDouble(27000);  // 拉回正午
  }
});
```
静态字段地址：`il2cpp_class_get_static_field_data(MainClass)` + 字段偏移
（实测 `time` 在 staticData+1168，`dayTime` 在 +1160）。

### 5.3 生成箱子
```js
WorldGen.PlaceChest(x, y, type=21, notNearOtherChests, style) → int 箱子索引（-1 失败）
// 全部参数按 4 字节写入；需 2x2 空地 + 下方支撑
```
实测成功：箱子索引 **319**，图块 **(3498, 346)**，容量 40。

### 5.4 钱币枪弹药
钱币 `ammo=71`，即钱币枪(`useAmmo=71`)的弹药。装入货币槽 50–53：
铜币×100、银币×100、金币×100、**铂金币×9999**（`maxStack=9999`）。

## 六、失败与事故

### 6.1 物品搬入箱子 → 游戏闪退

**操作**：直接交换数组指针
```js
chestItems[j] = playerItemObj;      // 箱子槽 ← 玩家物品对象
invData[srcSlot] = chestEmptyObj;   // 玩家槽 ← 箱子原对象
```

**后果**：游戏立即闪退。

**推测原因**（未验证）：
- 直接搬移 `Item` 对象指针破坏了两边数组的元素归属约定；
- 或玩家背包的**特殊槽位**（货币 50–53 / 弹药 54–57）的物品被移动后触发异常；
- 或 IL2CPP GC 对跨数组搬运的对象引用处理出现问题。

**正确做法应该是**：调用游戏自身的物品移动 API（如 `ItemSlot` 相关方法），
或复制 `Item` 字段内容而非交换对象指针；且应避开货币槽/弹药槽。

**存档状态**：`块状的蜂蜜传说.wld`（6.96MB）+ `.bak` 备份完好，
角色 `偶泥考.plr`（4000B）+ `.bak` 完好。崩溃未损坏存档。

### 6.2 "整理背包丢物品"调查结论

用户报告点击整理后大量物品消失（59 → 26 件）。

**实测证据**（主线程 hook 抓取，用户点击 3 次）：

```
>> SortInventory/0_ENTER            n=59
   >> SortAmmo/0_ENTER              n=59
      >> ClearAmmoSlotSpaces/0_ENTER   n=59
      << ClearAmmoSlotSpaces/0_LEAVE   before=59 after=59  lost=[] gained=[]
      >> FillAmmoFromInventory/0_ENTER n=59
      << FillAmmoFromInventory/0_LEAVE before=59 after=59  lost=[] gained=[]
   << SortAmmo/0_LEAVE              before=59 after=59  lost=[] gained=[]
<< SortInventory/0_LEAVE            before=59 after=59  lost=[] gained=[]
```

**结论**：整理流程 = `SortInventory → SortAmmo → ClearAmmoSlotSpaces → FillAmmoFromInventory`，
**只做重排序，零丢失、无异常**。满背包（59/59）同样不丢。

**那次消失的可能解释**：
- 抓到的唯一异常是 `Main.get_myPlayer()` 抛 NRE —— 但那是**跨线程调用**造成的，主线程正常；
- 我先前误判 `clientPlayer`（实为 `Terraria.Player` 对象指针）并写入 4 字节 0，
  游戏已自动重新赋值修复（现值 `0xb40000792bdc7be0` 完好）；
- 最可能是**当时的瞬时状态 + UI 未刷新**叠加，用户主观看到"枪没了"。

## 七、事故复盘要点

1. **写内存前先备份数据**：应当先完整快照物品数组，再执行有风险的操作。
2. **优先用游戏自身 API**：直接交换对象指针是危险操作，应调用游戏的物品移动方法。
3. **避开特殊槽位**：货币槽 50–53、弹药槽 54–57 有独立逻辑，不要往里塞普通物品。
4. **一次只做一个改动**：本次把"移动物品"和"箱子生成"叠在一起，崩溃后难以定位。
